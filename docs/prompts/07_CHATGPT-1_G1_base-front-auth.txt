B. PROJET
InvoiceFlow est une application web de facturation pour freelances et TPE du
Cameroun : factures conformes (NIU, RCCM, numérotation FAC-AAAA-MM-NNN, TVA
par ligne), proforma distincte, paiements partiels avec allocation, statuts,
PDF, envoi par email, tableau de bord. V1 sans IA. Projet portfolio, solo,
budget zéro, données de démonstration uniquement. Utilisateurs surtout sur
téléphone (réseau 3G/4G) : mobile-first. L'utilisateur est un étudiant qui
apprend en construisant (méthode « génération puis explication »).

D. CONVENTIONS
- Git : une branche par tâche, commits type « feat: ... », « fix: ... »,
  « test: ... ». Jamais de secret dans Git : seulement .env.example.
  Fins de ligne : LF (un .gitattributes « * text=auto eol=lf » est à la racine).
- Nommage : classes, propriétés et champs JSON en anglais camelCase. Tables
  et colonnes MySQL = exactement celles des diagrammes P02 (snake_case
  français). Valeurs d'énumération en MAJUSCULES françaises (BROUILLON,
  ENVOYEE...). Méthodes de service nommées comme dans les diagrammes de
  séquence, sans accents : envoyerFacture, prochainNumero, recalculer,
  enregistrerLigne, convertir, enregistrerPaiement, genererPdf, envoyerEmail.
- Structure backend : backend/src/<module>/ (module, controller, service,
  dto/). Entités partagées dans backend/src/database/entities/. Modules = P12.
- IDENTIFIANTS : entiers en base. En JSON, tous les id sont des `number`
  (id: 12, clientId: 3, taxRateId: 1, invoiceId: 7). Seuls les montants et
  quantités sont des chaînes décimales.
- ARGENT : jamais de float. DECIMAL(15,2) en base (quantité DECIMAL(12,3)).
  En JSON : chaînes décimales ("119250.00", "2.000"). Calculs avec decimal.js,
  ROUND_HALF_UP à 2 décimales, ligne par ligne. Les totaux d'un document sont
  la somme des montants de lignes déjà arrondis.
- Dates : émission, échéance, validité = "AAAA-MM-JJ". Horodatages ISO 8601
  UTC. « Aujourd'hui » = date du jour en Africa/Douala. Devise : "XAF" par
  défaut (champ conservé pour la V2).

E. RÈGLES DE GESTION (le code doit toutes les respecter)
RG1  Chaque utilisateur ne voit que ses données : filtre serveur sur chaque
     lecture ET chaque écriture ; ressource d'un autre utilisateur = 404.
RG2  Un client a plusieurs proformas et factures ; un document a un seul client.
RG3  Numéro de facture unique, séquentiel, sans trou, FAC-AAAA-MM-NNN
     (AAAA-MM = date d'envoi, fuseau Africa/Douala). Attribué à l'envoi, jamais
     à un brouillon. La date d'émission est fixée à l'envoi, avec la même date.
RG4  Une facture a au moins une ligne : description, quantité, prix unitaire
     HT, taux de TVA propre à la ligne.
RG5  Taux de TVA pris dans la table taux_tva (pas de saisie libre) ; le taux
     est copié dans la ligne (taux_applique) à sa création.
RG6  La proforma est distincte de la facture, sans numéro fiscal. Après
     conversion, elle reste ACCEPTEE.
RG7  Facture envoyée = verrouillée (montants, lignes, client, numéro). Toute
     correction passe par un nouveau document. Le backend l'impose ; l'UI le
     reflète.
RG8  Un paiement peut être réparti sur plusieurs factures ; une facture peut
     être payée en plusieurs fois. Solde = TTC - allocations. La somme des
     allocations = montant du paiement.
RG9  « En retard » = statut ENVOYEE ET échéance < aujourd'hui ET solde > 0.
     Calculé, jamais stocké. Idem NON_PAYEE / PARTIELLEMENT_PAYEE / PAYEE.
RG10 La facture affiche NIU et RCCM de l'émetteur, NIU du client si B2B
     (client ENTREPRISE) et le régime de TVA.
Statuts STOCKÉS : facture = BROUILLON | ENVOYEE ; proforma = BROUILLON |
ENVOYEE | ACCEPTEE | REFUSEE.

inconnu.

H. QUALITÉ (conseils SaaS retenus)
Sécurité backend : DTO validés (whitelist) ; userId jamais lu depuis le corps
de requête ; autorisation et filtre utilisateur sur chaque lecture et écriture
(masquer un bouton n'est pas une protection) ; requêtes paramétrées ;
transactions + verrous pour numérotation et paiements ; helmet ; limitation de
débit sur connexion/inscription/refresh ; secrets seulement dans l'environnement
(jamais Git, bundle ni logs) ; pas de mot de passe, jeton ni donnée excessive
dans les logs ; pas de stack trace ni debug en production ; migrations
versionnées, synchronize=false ; échapper tout HTML (PDF, email).
Accessibilité front (WCAG 2.2 AA) : HTML natif d'abord (button = action, a =
navigation) ; label visible sur chaque champ ; erreurs liées par
aria-describedby, aria-invalid, résumé d'erreurs ; tout au clavier, focus
visible, aucun piège ; modales : nom accessible, focus initial, confinement,
retour du focus ; contraste texte 4,5:1 et composants 3:1 ; cibles >= 24 px
(viser 44) ; reflow à 320 px et zoom 200 % ; jamais d'information par la couleur
seule ; prefers-reduced-motion ; états chargement / vide / erreur / succès /
hors connexion / droits insuffisants ; tableaux avec caption et th scope.
Performance : LCP <= 2,5 s, INP <= 200 ms, CLS <= 0,1 ; JS initial d'une route
< 150-200 Ko gzip ; découpage par route ; pas de bibliothèque lourde (graphiques,
éditeur riche) en V1 ; images avec dimensions explicites ; polices système ou
une seule famille (2 graisses max) ; annuler les requêtes obsolètes ; listes
paginées ; API p95 < 500 ms ; pas de requêtes N+1.
Tests : priorité aux calculs, à la numérotation, aux statuts, aux paiements
(valeurs vérifiées à la main) et à l'isolation entre utilisateurs A et B.
Un score d'outil automatique ne prouve pas la conformité.
